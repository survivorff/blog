# X Thread：做一个 Telegram 交易 Bot 到底有多难

> 推广文章：https://blog.frankfu.cloud/posts/telegram-trading-bot/
> 发布策略：开博后第 15 天左右，风格最"劝退"但也最引流的 Thread
> 目标：让"想做 Bot"的人理解真实难度，让"做过 Bot"的人会心一笑

---

## 推文序列（1/10）

### 1/10 — Hook

```
"不就是 Telegram Bot + Solana RPC + Swap 吗？几百行代码搞定。"

做过一年 Telegram 交易 Bot 后端的人告诉你：

想法很美好。真做一个能跑的，你会踩十几个坑。🧵
```

### 2/10 — 第一个坑：钱包安全

```
用户私钥放哪里？

A. 托管：速度最快，你为所有用户资金安全负责
B. 非托管：用户管理私钥，大部分用户不会用

90% 的 TG Bot 选 A。这意味着：
- HSM/KMS 加密存储
- 签名服务独立部署
- 操作审计 + 多签管理

一次安全事故 = 整个 Bot 死亡 + 法律问题。
```

### 3/10 — 第二个坑：Telegram API 限制

```
Bot API 速率限制：
- 单个聊天：30 条/秒
- 全局：30 条/秒

用户多了以后：
- 通知消息发不出去
- 止盈止损触发延迟
- 用户看不到成交通知

需要消息队列 + 限流，这是第一个必然的分布式架构问题。
```

### 4/10 — 第三个坑：状态管理

```
TG Bot 是无状态的。用户发 /buy abc 1，Bot 要判断：

- 新用户还是老用户
- 默认滑点设置
- 是否在多步操作的中间
- 是否有未完成订单
- 风控状态

Redis（快速）+ PostgreSQL（持久）是最低配。
```

### 5/10 — 第四个坑：并发原子性

```
用户发 /buy abc 0.1
然后立即发 /sell abc all

这两笔不能并发执行，要用用户级锁：

const lock = await acquireLock(`user:${uid}`);
try { /* execute */ } finally { lock.release(); }

还要考虑：多设备操作、自动交易 vs 手动操作冲突、跟单触发冲突。
```

### 6/10 — 第五个坑：跟单的扇出问题

```
假设平台 1 万用户，每人跟 5 个钱包，热门钱包有 1000+ 跟单者。

一个钱包的动作 → 触发上千个跟单交易。

这是发布-订阅扇出问题：
- 事件队列（Kafka / Redis Streams）
- 批处理优化
- 失败隔离

复杂度陡增一个量级。
```

### 7/10 — 第六个坑：RPC 成本

```
一个中等规模 TG Bot 的 RPC 费用：

**$5,000-$50,000/月。**

Bot 需要大量链上查询：
- 每次下单 3-5 次 RPC 调用
- 每秒同步所有活跃用户持仓
- 几十上百个 WebSocket 订阅

优化策略能省 60-80%，但不优化直接死。
```

### 8/10 — 第七个坑：止盈止损的可靠性

```
用户设"涨到 2x 自动卖出"。

最大陷阱：**服务器宕机，止盈止损不触发**。用户可能亏损甚至告你。

必须：
- 高可用部署 + 自动故障转移
- 任务持久化
- 分布式任务调度
- 兜底通知（至少告诉用户"监控中断"）

生产级可靠性是完全不同的工程量。
```

### 9/10 — 真实成本

```
一个月活 1 万、日交易量 $500 万的 TG Bot 的月成本：

- RPC: $5-15K
- 服务器: $3-8K
- Jito Tip 垫付: $2-10K
- 监控告警: $500-2K
- KMS/HSM: $500-2K
- 团队（3 人）: $30-60K

**总计: $40-100K/月**

收入（1% 费率）：约 $45K/月

早期 Bot 为什么活不下来？成本吃掉了一切。
```

### 10/10 — 给新手的建议

```
如果你想做 TG 交易 Bot：

1. 先想清楚商业模式，别"技术能做"就做
2. 安全放第一位，一次事故毁所有
3. RPC 成本从第一天就优化

另一个思路：**不做整个 Bot，做里面的组件。**
- 跟单引擎授权
- Token 安全评分 API
- RPC 聚合服务

**在饱和赛道直接竞争，不如做水电煤。**

完整版：blog.frankfu.cloud/posts/telegram-trading-bot/
```
